# ASR 모델 구조 쉬운 설명 가이드

아래는 당신이 정리한 트리를 유지하면서,
각 분류 사이에 "왜 이런 구조인지"를 쉬운 말로 풀어쓴 문서입니다.
핵심은 **CTC / RNNT / Seq2Seq가 무엇을 잘하고 무엇이 약한지**를 감으로 잡는 것입니다.

---

## ASR (Automatic Speech Recognition)

ASR은 말소리를 문자로 바꾸는 기술입니다.
실무에서는 보통 "정확도", "지연시간", "연산량" 세 가지를 동시에 맞춰야 합니다.
그래서 모델 구조를 고를 때도 이 세 가지 균형이 가장 중요합니다.
특히 스트리밍 서비스에서는 정확도 1~2%보다 지연 300ms 차이가 체감상 더 클 때가 많습니다.
결국 모델 선택은 "어디서 쓸 건지(회의록/콜센터/자막)"가 먼저입니다.

예문:
"안녕하세요, 오늘 회의는 오후 세 시에 시작합니다."

처리과정:
1. 마이크 입력을 16kHz 파형으로 수집합니다.
2. 파형을 mel-spectrogram 같은 특징으로 변환합니다.
3. ASR 모델이 프레임별/토큰별 확률을 계산합니다.
4. 디코더가 가장 타당한 문장 후보를 선택합니다.
5. 후처리(띄어쓰기/구두점/고유명사 사전)로 최종 문장을 정리합니다.

---

## 1. Alignment-based models

이 계열은 "오디오 프레임과 문자 토큰을 어떻게 맞출지(alignment)"가 핵심입니다.
문장 전체를 한 번에 생성하기보다, 시간축 프레임을 따라가며 해석합니다.
그래서 구조가 비교적 단순하고, 학습/추론 파이프라인이 안정적인 편입니다.
스트리밍처럼 시간 순서가 중요한 환경에서 다루기 쉽습니다.
대표가 CTC이고, 많은 산업 시스템에서 여전히 강력한 기본 선택지입니다.

예문:
사용자 발화 "지금 서울 날씨 알려줘"를 100ms 단위 프레임으로 나눠 본다고 가정합니다.

처리과정:
1. 0.0~0.1초 프레임에서 "지" 가능성을 계산합니다.
2. 0.1~0.2초 프레임에서 blank 또는 "금"을 계산합니다.
3. 전체 프레임을 시간 순으로 연결해 가장 자연스러운 토큰 경로를 찾습니다.
4. 중복 토큰과 blank를 제거해 "지금 서울 날씨 알려줘"를 만듭니다.
5. 필요하면 LM으로 문맥 점수를 더해 최종 후보를 선택합니다.

### 1-1. CTC (Connectionist Temporal Classification)

#### Core idea
- frame-level token prediction
- blank token alignment
- token independence assumption

CTC를 쉬운 말로 하면 "매 프레임마다 글자를 맞혀보고, 필요 없는 칸(blank)은 지우는 방식"입니다.
예를 들어 같은 글자가 연속으로 나와도 blank를 사이에 둬서 경계를 표현할 수 있습니다.
그래서 발화 길이와 문자 길이가 달라도 학습이 가능합니다.
다만 기본 CTC는 토큰 간 의존성을 약하게 보기 때문에 문맥 문장력은 상대적으로 약할 수 있습니다.
이 약점을 보완하려고 LM 결합이나 강한 인코더를 함께 씁니다.

예문:
프레임 출력이 `[ㅎ, blank, ㅏ, blank, ㄴ, ㄱ, blank, ㅜ, ㄱ]`처럼 나왔을 때를 생각해봅시다.

처리과정:
1. 먼저 시간축 프레임 출력을 왼쪽에서 오른쪽으로 읽습니다.
2. 연속 중복 토큰을 축약합니다.
3. blank 토큰을 제거합니다.
4. 남은 토큰을 결합해 "한국" 같은 문자열 후보를 복원합니다.
5. 후보 중 확률이 가장 높은 경로를 최종 출력으로 채택합니다.

#### Architecture
- Encoder-only

CTC가 실무에서 인기가 많은 이유 중 하나가 Encoder-only 구조입니다.
디코더가 없거나 매우 단순해서 추론이 빠르고 구현 복잡도가 낮습니다.
서버 비용과 모바일 전력 측면에서 유리합니다.
대신 "문장 생성 능력"은 디코더 기반 모델보다 약할 수 있어 후처리 품질이 중요합니다.
즉, 빠르고 안정적이지만 언어적 자연스러움은 보강이 필요한 타입입니다.

#### Encoder types
- CNN
- RNN / LSTM
- Transformer
- Conformer

인코더는 "소리를 얼마나 잘 표현하느냐"를 결정합니다.
예전에는 RNN/LSTM이 많았고, 요즘은 Transformer/Conformer가 주류입니다.
Conformer는 self-attention(전역 문맥) + convolution(지역 패턴)을 같이 써서 음성에 특히 강합니다.
같은 CTC라도 인코더가 바뀌면 성능 차이가 크게 납니다.
그래서 최근 CTC 성능이 과거 인식과 달리 꽤 높아졌습니다.

#### CTC variants

##### Classical CTC
- limited temporal context
- mostly acoustic modeling

고전 CTC는 시간 문맥을 길게 보기 어려워 "소리 맞히기" 중심이었습니다.
그래서 발음이 비슷한 단어를 문맥으로 구분하는 능력이 제한적이었습니다.
짧은 명령어 인식에는 충분했지만 긴 문장에서는 한계가 드러났습니다.
이 시기 모델은 빠르고 단순하지만 문장 자연스러움이 약했습니다.
그래도 실시간성과 안정성 측면에서는 여전히 장점이 있었습니다.

##### Modern CTC
- transformer encoder
- strong context modeling
  - self-attention
  - long receptive field
  - contextual frame representations
- multi-task learning
  - emotion recognition
  - speaker traits
  - event detection
  - language ID

현대 CTC는 사실상 "강한 인코더 + 멀티태스크"로 진화한 형태입니다.
self-attention 덕분에 먼 구간 문맥도 반영할 수 있어 오인식이 줄었습니다.
또 감정/화자/언어ID를 함께 학습하면 인코더 표현이 더 풍부해집니다.
그래서 과거의 "CTC=문맥 약함" 공식이 많이 완화되었습니다.
요약하면, 현대 CTC는 속도 장점은 유지하면서 정확도 약점을 상당히 메웠습니다.

#### Language Model integration
- no LM (pure acoustic decoding)
- external n-gram LM
- neural LM

LM 결합은 CTC의 문맥 약점을 메우는 가장 전통적인 방법입니다.
n-gram LM은 가볍고 빠르며, 도메인 문구를 추가하기 쉽습니다.
neural LM은 더 강력하지만 연산량과 운영 복잡도가 늘어납니다.
서비스에서는 지연시간 요구에 따라 LM 강도를 조절합니다.
즉 "정확도 올릴수록 비용/지연이 늘 수 있다"는 트레이드오프입니다.

예문:
음향만 보면 "회사를"과 "회사로"가 비슷하게 들리는 구간이 있다고 가정합니다.

처리과정:
1. CTC가 두 문장 후보를 비슷한 점수로 냅니다.
2. 외부 LM이 앞뒤 문맥("내일 회사를 간다")의 확률을 계산합니다.
3. LM 점수가 높은 "회사를" 후보가 선택됩니다.
4. beam search는 이 과정을 여러 후보에 병렬 적용합니다.
5. 최종적으로 음향 점수 + LM 점수 합산값이 최대인 문장을 출력합니다.

#### Decoding strategies
- greedy decoding
- beam search + LM

greedy는 가장 빠르지만 실수 복구가 어렵습니다.
beam search는 여러 후보를 유지해 더 나은 결과를 찾습니다.
LM을 함께 쓰면 문장 자연스러움이 좋아지는 경우가 많습니다.
대신 beam 크기가 커질수록 지연시간이 늘어납니다.
그래서 실시간 시스템은 보통 작은 beam + 제한된 LM으로 타협합니다.

#### Audio inference style
- chunk-based inference
- overlapping chunks
- stride merging

긴 오디오를 통째로 넣기 어렵기 때문에 chunk 단위 추론을 많이 씁니다.
overlap은 경계에서 단어가 잘리는 문제를 줄여줍니다.
stride merging은 겹친 구간 결과를 합쳐 최종 텍스트를 만듭니다.
이 과정 설계가 나쁘면 결과가 깜빡이거나 반복 토큰이 생깁니다.
즉 모델만큼이나 "청크 병합 로직"이 품질에 중요합니다.

예문:
6초 발화를 2초 청크 + 0.5초 오버랩으로 처리한다고 가정합니다.

처리과정:
1. 청크1(0.0~2.0), 청크2(1.5~3.5), 청크3(3.0~5.0)처럼 겹치게 자릅니다.
2. 각 청크에서 부분 문장을 독립 추론합니다.
3. 겹친 구간(예: 1.5~2.0초)에서 공통 토큰을 정렬합니다.
4. 중복 토큰을 제거하고 앞/뒤 청크를 이어 붙입니다.
5. 병합 후 띄어쓰기/문장부호 보정을 적용해 깔끔한 문장으로 만듭니다.

#### Streaming capability
- pseudo-streaming (chunk)
- low latency chunk inference

CTC는 진짜 프레임 단위 스트리밍이라기보다, 청크 기반 의사 스트리밍이 흔합니다.
그래도 청크를 작게 잡으면 체감상 거의 실시간처럼 동작합니다.
반면 너무 작게 잡으면 문맥이 약해져 오인식이 늘 수 있습니다.
실무에서는 청크 길이와 overlap을 함께 튜닝합니다.
결론적으로 CTC는 저지연 서비스에 매우 실용적인 선택지입니다.

#### Example models
- Wav2Vec2
- SenseVoice

Wav2Vec2는 자기지도 사전학습 덕분에 다양한 환경에서 강력합니다.
SenseVoice는 멀티태스크/실사용 지향 특성이 강조된 계열로 자주 언급됩니다.
다만 같은 이름의 모델도 설정(토크나이저, 디코더, LM) 따라 성능이 크게 달라집니다.
그래서 "모델명"보다 "운영 설정"을 같이 봐야 공정한 비교가 됩니다.
벤치마크 숫자만 보고 바로 적용하면 현장 성능이 달라질 수 있습니다.

### 1-2. Alignment mechanism
- dynamic programming (forward-backward)

CTC 학습의 수학적 핵심은 forward-backward 동적계획법입니다.
정답 문장에 대응되는 가능한 정렬 경로를 모두 합산해 확률을 계산합니다.
덕분에 프레임-토큰 정렬 라벨을 사람이 직접 만들 필요가 없습니다.
이 점이 CTC를 대규모 학습에 유리하게 만듭니다.
즉 "정렬 불확실성"을 수학적으로 흡수한 것이 CTC의 큰 장점입니다.

예문:
정답 텍스트가 "가방"이고 프레임이 8개일 때, 가능한 정렬은 여러 가지입니다.

처리과정:
1. "가-blank-방", "blank-가-방", "가-가-blank-방" 같은 경로를 나열합니다.
2. forward 단계에서 시작점부터 누적 확률을 계산합니다.
3. backward 단계에서 끝점부터 역방향 누적 확률을 계산합니다.
4. 두 값을 결합해 각 시점의 정렬 기여도를 얻습니다.
5. 전체 경로 확률 합으로 손실을 계산해 모델을 학습합니다.

## 2. Transducer models

Transducer는 스트리밍 ASR에서 매우 중요한 계열입니다.
핵심은 소리 정보(Encoder)와 언어 정보(Predictor)를 결합해 다음 토큰을 내는 방식입니다.
CTC보다 토큰 의존성을 자연스럽게 다룰 수 있어 문장 품질이 좋아지는 경우가 많습니다.
동시에 순차 처리 구조라 실시간 서비스와 궁합이 좋습니다.
대표가 RNNT이며, 대형 제품 서비스에서 널리 사용됩니다.

예문:
콜센터 실시간 자막에서 상담사 발화를 거의 지연 없이 띄워야 하는 상황을 생각해봅시다.

처리과정:
1. Encoder가 들어오는 오디오 프레임을 순차적으로 인코딩합니다.
2. Predictor가 직전 출력 토큰 히스토리를 유지합니다.
3. Joiner가 두 상태를 합쳐 현재 토큰 확률을 계산합니다.
4. 토큰이 확정되면 즉시 화면에 반영합니다.
5. 다음 프레임에서도 같은 상태를 이어받아 연속적으로 처리합니다.

### 2-1. RNNT (Recurrent Neural Network Transducer)

#### Core idea
- joint acoustic + language modeling
- token emission events

RNNT는 "언제 글자를 낼지" 자체를 모델링합니다.
CTC처럼 프레임별 독립 가정이 강하지 않아 문맥 활용이 더 자연스럽습니다.
Predictor가 내부 LM 역할을 하면서 문장 연결성을 높입니다.
그래서 스트리밍에서도 품질과 지연의 균형이 좋습니다.
다만 구조가 CTC보다 복잡해 학습/디버깅 난이도는 높습니다.

예문:
발화 "내일 오후 두 시"에서 "두"를 내보낼 시점을 모델이 스스로 결정합니다.

처리과정:
1. Encoder가 "내일 오후" 구간 특징을 만듭니다.
2. Predictor는 이미 출력된 "내일 오후" 토큰을 기억합니다.
3. Joiner는 현재 음향과 이전 문맥을 같이 보고 "두" 방출 확률을 계산합니다.
4. 확률이 임계값을 넘으면 "두"를 즉시 출력합니다.
5. 이어서 "시" 토큰도 같은 방식으로 순차 결정합니다.

#### Architecture
- Encoder
  - acoustic representation
  - temporal context modeling
- Predictor
  - internal language model
- Joiner
  - combines encoder + predictor states

RNNT는 세 블록이 역할 분담을 명확히 합니다.
Encoder는 소리 특징, Predictor는 이전 토큰 문맥을 담당합니다.
Joiner가 둘을 합쳐 실제 출력 확률을 만듭니다.
이 분리가 잘 되면 스트리밍 중에도 안정적으로 토큰을 방출합니다.
반대로 어느 한쪽이 약하면 전체 품질이 빠르게 무너질 수 있습니다.

예문:
사용자 발화 "회의는 내일 아침 열 시"를 처리할 때의 블록별 역할입니다.

처리과정:
1. Encoder는 음성 스펙트럼에서 자음/모음 패턴을 뽑습니다.
2. Predictor는 이미 출력된 "회의는 내일" 문맥을 유지합니다.
3. Joiner는 둘을 합쳐 "아침" 또는 "오전" 후보 확률을 냅니다.
4. 더 높은 확률 후보를 선택해 토큰을 확정합니다.
5. 토큰 확정 후 Predictor 상태를 갱신해 다음 단어 예측에 반영합니다.

#### Encoder types
- LSTM
- Conformer
- Zipformer

초기 RNNT는 LSTM이 많았고, 최근은 Conformer/Zipformer가 강세입니다.
Zipformer는 속도와 성능 균형을 겨냥해 설계된 경우가 많습니다.
같은 RNNT라도 Encoder 선택이 지연/정확도를 크게 좌우합니다.
특히 온디바이스에서는 경량 Encoder가 매우 중요합니다.
운영 환경(CPU/GPU/NPU)에 맞춰 선택해야 실효 성능이 나옵니다.

#### Decoding
- greedy transducer decoding
- beam search transducer decoding

RNNT도 greedy가 가장 빠르고, beam이 더 정확한 경향입니다.
다만 transducer beam은 구현 최적화가 성능에 큰 영향을 줍니다.
beam 폭이 넓으면 정확도는 오르지만 지연과 메모리가 증가합니다.
실시간 제품은 보통 small beam으로 타협합니다.
최적점은 서비스 요구 latency SLA에 따라 달라집니다.

예문:
실시간 자막 서비스에서 목표 지연이 300ms 이하라고 가정합니다.

처리과정:
1. 먼저 greedy로 측정해 기준 지연/정확도를 기록합니다.
2. beam=2, beam=4로 올리며 WER과 p95 latency를 함께 비교합니다.
3. SLA를 넘는 설정은 제외합니다.
4. 남은 후보 중 정확도가 가장 높은 설정을 선택합니다.
5. 운영 중 트래픽 증가 시 beam을 자동 축소하는 정책도 함께 둡니다.

#### Audio processing
- frame-by-frame inference

RNNT의 강점은 프레임 단위 진행이 자연스럽다는 점입니다.
새 오디오가 들어오면 상태를 이어받아 바로 계산할 수 있습니다.
그래서 "대기했다가 한 번에 처리"가 아니라 지속 처리에 적합합니다.
이는 회의 자막, 콜센터 모니터링처럼 연속 입력에서 유리합니다.
체감 지연이 낮아 사용자 경험이 좋습니다.

#### Streaming capability
- true real-time streaming
- encoder state propagation
- predictor state propagation

RNNT는 상태 전파(state propagation)를 통해 진짜 스트리밍을 구현합니다.
매번 처음부터 계산하지 않고 이전 상태를 재사용합니다.
덕분에 지연과 연산량을 함께 줄일 수 있습니다.
다만 상태 관리 버그가 있으면 누적 오류가 생기기 쉽습니다.
그래서 프로덕션에서는 상태 초기화/재동기화 정책이 매우 중요합니다.

예문:
사용자가 20초 길이 문장을 말할 때 매 프레임마다 처음부터 재계산하면 지연이 커집니다.

처리과정:
1. 프레임 t에서 계산한 encoder/predictor 상태를 캐시에 저장합니다.
2. 프레임 t+1에서 캐시 상태를 불러와 이어서 계산합니다.
3. 무음 구간이 길면 세션 경계를 만들어 상태를 리셋합니다.
4. 네트워크 끊김/패킷 손실 시 재동기화 지점을 적용합니다.
5. 상태 누락이 감지되면 안전 모드(부분 재계산)로 복구합니다.

#### Internal language modeling
- predictor acts as LM

Predictor 자체가 LM 역할을 해 외부 LM 의존도를 낮출 수 있습니다.
이는 시스템 단순화에 도움이 됩니다.
하지만 특정 도메인 용어를 빠르게 반영하려면 외부 보강이 여전히 필요할 수 있습니다.
예를 들어 고유명사, 신조어, 상품명은 별도 적응이 필요합니다.
즉 내부 LM은 기본기, 외부 보강은 도메인 특화라고 보면 이해가 쉽습니다.

#### Example models
- Conformer-RNNT
- Zipformer-RNNT

Conformer-RNNT는 품질 지향, Zipformer-RNNT는 효율 지향으로 많이 비교됩니다.
실제 우열은 데이터셋/하드웨어/디코더 구현에 따라 달라집니다.
그래서 공개 리더보드 결과를 그대로 믿기보다 내부 데이터로 재검증해야 합니다.
특히 한국어는 조사/띄어쓰기 특성 때문에 튜닝 포인트가 다릅니다.
프로젝트 기준 지표(CER/WER, latency, flicker)를 함께 봐야 정확합니다.

## 3. Attention-based / Seq2Seq models

이 계열은 "문장을 생성"하는 관점이 강합니다.
Decoder가 이전 토큰을 보고 다음 토큰을 내는 자기회귀 방식입니다.
문장 자연스러움과 전역 문맥 활용이 강점입니다.
반면 스트리밍 지연 측면에서는 불리한 경우가 많습니다.
대표적으로 Whisper가 여기에 속합니다.

예문:
긴 발표 음성에서 "그때 그 정책이 왜 바뀌었는지" 같은 문맥 의존 표현을 처리할 때 강합니다.

처리과정:
1. Encoder가 긴 구간 음성을 고차원 표현으로 변환합니다.
2. Decoder가 시작 토큰부터 순차적으로 단어를 생성합니다.
3. 이전에 생성한 단어들을 문맥으로 계속 재참조합니다.
4. 애매한 단어는 앞뒤 의미를 보고 더 자연스러운 쪽으로 선택합니다.
5. 문장 끝까지 반복해 최종 텍스트 시퀀스를 완성합니다.

### Core idea
- sequence generation
- autoregressive decoding

Seq2Seq는 프레임 정렬보다 "최종 텍스트 시퀀스 품질"에 집중합니다.
그래서 긴 문맥에서 의미적으로 더 자연스러운 문장을 만들 수 있습니다.
하지만 토큰을 순차 생성하므로 추론 지연이 누적될 수 있습니다.
실시간 서비스에서는 바로 이 점이 병목이 됩니다.
요약하면 품질은 강하지만 지연 최적화가 과제입니다.

예문:
"오늘은 비가 오지만 내일은 맑겠습니다" 같은 접속 구문에서 문장 흐름을 잘 잡습니다.

처리과정:
1. Decoder가 "오늘은"을 생성합니다.
2. 다음 토큰 생성 시 "오늘은"을 조건으로 사용합니다.
3. 이어지는 "비가 오지만" 문맥을 반영해 다음 단어를 예측합니다.
4. 문장 후반 의미까지 고려해 표현을 조정합니다.
5. 결과적으로 전체 문장 자연스러움이 개선됩니다.

### Architecture
- Encoder
  - acoustic feature extraction
- Decoder
  - autoregressive token generation
  - acts as language model

Encoder가 오디오를 표현으로 바꾸고, Decoder가 문장을 생성합니다.
Decoder는 사실상 강한 LM이라 문법적 자연스러움에 유리합니다.
대신 Decoder 연산이 무거우면 실시간성이 떨어집니다.
그래서 서버 GPU 환경에서는 잘 맞고, 저전력 디바이스에서는 부담이 될 수 있습니다.
아키텍처 선택은 배포 환경을 먼저 보고 결정해야 합니다.

### Mechanism
- cross-attention
  - decoder attends to encoder frames

cross-attention은 Decoder가 필요한 오디오 구간을 참조하게 해줍니다.
덕분에 문맥 기반 수정 능력이 좋아집니다.
특히 애매한 발음을 주변 단어 문맥으로 교정하는 데 유리합니다.
하지만 전체 표현을 넓게 보게 되면 계산량이 증가합니다.
그래서 저지연에서는 attention 범위를 제한하는 변형이 자주 쓰입니다.

예문:
오디오상 "사과"와 "사가"가 헷갈리는 구간에서 다음 단어가 "먹었다"라면 "사과"가 더 자연스럽습니다.

처리과정:
1. Decoder가 현재 생성 위치에서 encoder 프레임 전체를 조회합니다.
2. 애매 구간 주변 프레임 가중치를 높여 정보를 모읍니다.
3. 언어 문맥("먹었다")과 음향 단서를 함께 평가합니다.
4. 더 일관된 토큰("사과")을 선택합니다.
5. 선택 결과를 다음 토큰 생성의 조건으로 넘깁니다.

### Language modeling
- decoder inherently models language

Seq2Seq는 구조적으로 LM을 내장하고 있습니다.
그래서 별도 LM 없이도 자연스러운 문장을 만들 가능성이 높습니다.
반면 도메인 특화 제어는 외부 LM 결합형보다 어려울 때가 있습니다.
용어 강제 삽입, 발음 사전 반영은 추가 기법이 필요합니다.
즉 "기본 문장력 강함"과 "제어 난이도"가 함께 따라옵니다.

### Audio inference
- full sequence inference
- chunk-based pseudo streaming
  - audio chunks
  - overlap
  - prompt reuse
  - partial output revision

원래는 전체 오디오를 보고 추론하는 방식이 기본입니다.
스트리밍이 필요하면 청크+오버랩+프롬프트 재사용으로 흉내냅니다.
이때 이전 결과를 일부 수정하는 로직이 필수입니다.
수정 정책이 약하면 자막이 자주 흔들립니다.
그래서 실제 제품에서는 "부분 확정 + 꼬리 구간만 수정" 전략을 같이 씁니다.

예문:
10초 발화를 3초 단위로 재해석하는 반실시간 보정 파스를 구성한다고 가정합니다.

처리과정:
1. 0~3초 청크를 추론해 임시 텍스트를 출력합니다.
2. 2~5초 청크를 추론하면서 이전 꼬리 1초를 겹쳐 봅니다.
3. 공통 구간은 고정하고, 마지막 3~5단어만 수정 허용합니다.
4. 다음 4~7초 청크에서도 같은 규칙으로 tail만 교정합니다.
5. 무음/VAD 경계에서 최종 commit하여 흔들림을 줄입니다.

### Streaming capability
- semi-streaming
- higher latency

Seq2Seq는 완전 실시간보다 반실시간(세미 스트리밍)에 더 맞는 경우가 많습니다.
정확도는 높지만 응답 지연이 상대적으로 큽니다.
그래서 라이브 자막에서는 1차 스트리밍 모델 + 2차 Seq2Seq 보정 조합이 흔합니다.
당신이 말한 0.1초 + 1.5/3초 구조와 잘 맞는 이유가 여기에 있습니다.
즉 Seq2Seq는 "보정기"로 쓸 때 가치가 크게 올라갑니다.

예문:
1차 RNNT가 즉시 "오늘 회의 시작합니다"를 띄우고, 2차 Seq2Seq가 "오늘 회의 시작하겠습니다"로 보정하는 패턴입니다.

처리과정:
1. 1차 모델이 100ms 간격으로 초저지연 텍스트를 출력합니다.
2. 2차 모델이 1.5초 또는 3초 윈도우로 재디코딩합니다.
3. 확정 prefix는 유지하고 mutable tail만 교체합니다.
4. 사용자 화면에는 바뀐 부분만 최소 단위로 업데이트합니다.
5. 결과적으로 체감 지연은 낮고 최종 정확도는 높아집니다.

### Global context modeling
- decoder uses entire audio representation

전역 문맥을 넓게 보는 능력은 Seq2Seq의 핵심 장점입니다.
문장 끝에서 앞의 의미를 다시 반영해 교정할 수 있습니다.
긴 발화, 담화 문맥, 고유명사 복구에 유리합니다.
하지만 이 장점은 동시에 지연 증가와 계산량 증가를 동반합니다.
그래서 서비스 목표에 따라 어디까지 전역 문맥을 허용할지 정해야 합니다.

### Example models
- Whisper
- SpeechT5

Whisper는 강한 일반화 성능으로 널리 사용됩니다.
SpeechT5는 음성/언어 멀티모달 관점에서 연구적으로 중요합니다.
다만 실제 제품 성능은 모델 자체보다 전처리, 디코딩, 후처리 영향이 큽니다.
특히 스트리밍 적용 시 chunk/overlap/prompt 전략이 결과를 크게 좌우합니다.
그래서 "모델 선택 + 운영 전략"을 하나의 세트로 봐야 합니다.

## 빠른 비교 요약

- CTC: 빠르고 단순하며 실시간 친화적, 문맥 보강이 필요할 수 있음.
- RNNT: 실시간성과 문맥의 균형이 좋고 산업 적용이 많음.
- Seq2Seq: 문장 품질과 전역 문맥 강점, 지연이 커서 보정 패스로 유리.
- 실전 추천: 1차 스트리밍(CTC/RNNT) + 2차 반실시간(Seq2Seq/강한 디코더) 2-pass.
- 운영 핵심: 모델 자체보다 `commit 정책`, `tail rewrite`, `flicker 제어`가 UX를 좌우.
