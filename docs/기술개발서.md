# 실시간 한국어 자막 파이프라인 기술개발서

**프로젝트명:** hybrid1 — Two-Stage Streaming Korean ASR Subtitle Pipeline
**플랫폼:** Raspberry Pi 5 (aarch64) / x86_64
**작성일:** 2026-03-30

---

## 1. 개요

### 1.1 목적

본 프로젝트는 **실시간 음성인식(ASR) 기반 한국어 자막 시스템**을 구현한다. 핵심 목표는 두 가지이다:

1. **즉시성** — 발화와 동시에 자막이 표시되어야 한다 (체감 지연 < 0.5초)
2. **정확성** — 최종 자막은 문맥을 반영한 고품질 텍스트여야 한다

이 두 목표는 본질적으로 상충한다. 실시간 스트리밍 모델은 빠르지만 정확도가 낮고, 오프라인 모델은 정확하지만 전체 발화가 끝나야 결과를 낼 수 있다. 본 시스템은 **2단계 하이브리드 파이프라인**으로 이 문제를 해결한다.

### 1.2 시스템 구성

```
┌─────────────────────────────────────────────────────────────────┐
│                        Audio Input                              │
│              WAV File / Microphone (16kHz mono)                 │
└──────────────────┬──────────────────────────────────────────────┘
                   │ 0.1초 프레임 단위 스트리밍
         ┌─────────┴─────────┐
         ▼                   ▼
  ┌──────────────┐   ┌───────────────┐
  │  1차: LIVE   │   │  2차: REFINE  │
  │  Transducer  │   │  SenseVoice   │
  │  (스트리밍)   │   │   (오프라인)   │
  │  지연 ~0.3초  │   │  지연 ~3~4초   │
  │  CER ~15%    │   │  CER ~5%      │
  └──────┬───────┘   └──────┬────────┘
         │                   │
         ▼                   ▼
  ┌─────────────────────────────────────┐
  │         SubtitleStore               │
  │   LIVE + REFINE 자막 병합(overlay)   │
  └──────────────────┬──────────────────┘
                     ▼
              최종 자막 출력
        (WebSocket / Console)
```

| 구성요소 | 모델 | 역할 | 특성 |
|---------|------|------|------|
| 1차 LIVE | Zipformer Transducer (sherpa-onnx) | 즉시 자막 표시 | 낮은 지연, 중간 정확도 |
| 2차 REFINE | SenseVoice Small (sherpa-onnx) | 보정 자막 교체 | 높은 정확도, 청크 단위 처리 |
| VAD | Silero VAD | 마이크 입력 시 음성 구간 감지 | 침묵 감지 → 자동 종료 |
| 띄어쓰기 | quickspacer (level=3) | 한국어 띄어쓰기 보정 | 후처리 단계 적용 |

### 1.3 기술 스택

- **Runtime:** Python 3.11+, sherpa-onnx (ONNX Runtime)
- **Server:** FastAPI + WebSocket (uvicorn)
- **Audio:** librosa, soundfile, sounddevice
- **모델 포맷:** ONNX (int8 양자화 지원)
- **프로세스 구조:** multiprocessing (spawn), Queue 기반 IPC

## 2. 1차 자막: Transducer Stage (LIVE)

### 2.1 동작 원리

Streaming Transducer 모델(Zipformer 기반)은 0.1초 프레임 단위로 오디오를 입력받아 **증분(incremental)** 텍스트를 출력한다.

```
프레임 1 (0.0~0.1초) → ""
프레임 2 (0.1~0.2초) → ""
  ...
프레임 25 (2.4~2.5초) → "이천"
프레임 26 (2.5~2.6초) → "이천 십"
프레임 30 (2.9~3.0초) → "이천 십 오 년"
```

### 2.2 LCP(Longest Common Prefix) 기반 증분 업데이트

매 프레임마다 전체 텍스트를 재출력하면 화면이 깜빡인다. 이를 방지하기 위해 **이전 토큰 리스트와의 최장 공통 접두사(LCP)** 를 비교하여 새로 추가된 토큰만 보고한다.

```
이전 토큰: [이천, 십, 오]
현재 토큰: [이천, 십, 오, 년, 현재]

LCP = 3 (처음 3개 일치)
→ 새 토큰: [년, 현재] (인덱스 3부터)
→ start_sec = timestamps[3]
```

### 2.3 출력 형태

```
[LIVE]       00:02.400 ~ 00:04.200 | 이천 십 오 년 현재
[LIVE]       00:02.400 ~ 00:05.100 | 이천 십 오 년 현재 음성
[LIVE-FINAL] 00:02.400 ~ 00:09.800 | 이천 십 오 년 현재 음성 인식 기술은
```

LIVE-FINAL은 스트리밍 종료 시점에 발행되며, 이후 REFINE 결과로 교체된다.

## 3. 2차 자막: SenseVoice Refine Stage (REFINE)

### 3.1 문제 정의

오프라인 모델(SenseVoice)은 전체 오디오를 한 번에 처리하면 최고 정확도를 보이지만, 발화가 끝날 때까지 기다려야 하므로 실시간 자막에 부적합하다. 따라서 오디오를 **청크(chunk) 단위**로 분할하여 점진적으로 처리해야 한다.

이때 청킹 전략에 따라 정확도와 실시간성의 트레이드오프가 크게 달라진다.

### 3.2 청킹 전략의 진화

#### 전략 1: Full Text (VAD 기반 전체 입력)

```
[===========전체 발화===========] → 한 번에 디코딩
```

- **장점:** 최고 정확도 (CER ~4.5%)
- **단점:** 실시간성 없음. 발화가 끝나야 결과 출력

#### 전략 2: Simple Chunking (단순 청킹)

```
[chunk1][chunk2][chunk3][chunk4]  → 각각 독립 디코딩
  4초     4초     4초     4초
```

- **장점:** 실시간성 확보, 구현 단순
- **단점:**
  - **잘림 현상** — 단어 중간에서 오디오가 잘려 "딥러이"(→딥러닝) 같은 불완전 토큰 발생
  - **중복 현상** — 인접 청크 경계에서 동일 단어가 양쪽에 출현
  - **문맥 부족** — 각 청크가 독립적이라 앞뒤 문맥 활용 불가
- **CER:** ~8.8%

**중복 해결:** `_dedup_overlap()` — 이전 커밋 텍스트의 접미사와 새 텍스트의 접두사를 문자 단위로 비교하여 겹치는 부분 제거

#### 전략 3: Overlapped Chunking (중첩 청킹 + Center-Commit)

```
[===chunk1===]
       [===chunk2===]
              [===chunk3===]

각 청크에서 중앙(center) 구간만 커밋, 양끝(trim)은 버림
```

- **개선:**
  - `trim_sec` 양쪽 여유로 **잘림 현상** 방지 (right_trim: 불완전 토큰 방지)
  - 토큰 타임스탬프 기반으로 center 구간만 정밀 추출
  - 양쪽 trim으로 약간의 문맥 확보
- **한계:**
  - trim은 좌우 각 0.5초 수준이 한계 → 문맥이 여전히 부족
  - 예: `0~4`를 보고 `0~3.5` 커밋, `3~7`을 보고 `3.5~6.5` 커밋
  - 각 디코딩에 주어지는 문맥은 최대 4초 (= 청크 크기)

#### 전략 4: Accumulated Context Chunking (누적 문맥 청킹) — **현재 구현**

```
청크0: [0━━━━4]                     → 디코딩: 0~4초    → 커밋: 0~3.5초
청크1: [0━━━━4━━━━8]                → 디코딩: 0~8초    → 커밋: 3.5~7.5초
청크2: [0━━━━4━━━━8━━━━12]          → 디코딩: 0~12초   → 커밋: 7.5~11.5초
청크3: [4━━━━8━━━━12━━━━16]         → 디코딩: 4~16초   → 커밋: 11.5~15.5초
          ↑ 최대 4개 초과 시 맨 앞 청크 제거 (FIFO)
```

- **핵심 아이디어:** 새 청크를 받을 때마다 이전 청크들을 누적하여 함께 디코딩
- **장점:**
  - 문맥이 점점 커지므로 **문장 후반부에서 정확도 현저히 향상**
  - 청크 1~2개째는 전략 3과 유사하나, 3~4개째부터 문맥 효과 극대화
- **CER:** ~5.5% (전략 1의 4.5%에 근접)

### 3.3 누적 문맥 청킹 상세 플로우

`SenseVoiceRefineStage._feed_center_commit()` 의 처리 흐름:

```
① full_chunk 생성
   이전 컨텍스트 버퍼 + 새 오디오 = 하나의 긴 오디오
   예: 청크2 → full_chunk = [청크0 | 청크1 | 청크2]

② trim 경계 설정
   left_trim  = context_dur - trim_sec  (이미 커밋된 구간 건너뜀, trim_sec 여유)
   right_trim = trim_sec                (불완전 토큰 방지)

③ SenseVoice 디코딩
   full_chunk 전체를 모델에 입력 → tokens + timestamps 획득

④ center 토큰 추출
   [left_trim, chunk_dur - right_trim] 구간의 토큰만 추출

⑤ 중복 제거 및 커밋
   _dedup_overlap으로 이전 텍스트와 겹침 제거 후 committed_text에 추가

⑥ 청크 버퍼 갱신
   새 청크 추가, 최대 4개 초과 시 맨 앞 제거 (FIFO)
```

### 3.4 버퍼 관리와 SenseVoice 제약

SenseVoice 모델은 **최대 약 30초까지 안정적**으로 처리 가능하다. 끊임없는 발화 시 누적 버퍼가 무한히 커지면:

1. **RTF(Real-Time Factor) 증가** — 처리 시간이 실시간을 초과
2. **2차 보정 자막과 1차 자막 사이의 시간 괴리** 확대
3. **메모리 사용량** 지속 증가

**해결: FIFO 청크 버퍼 (max_context_chunks = 4)**

```python
self._chunk_buffers.append(new_samples)
if len(self._chunk_buffers) > self._max_context_chunks:
    self._chunk_buffers.pop(0)       # 가장 오래된 청크 제거
self._context_buffer = np.concatenate(self._chunk_buffers)
```

chunk_sec=4.0 기준 최대 누적 입력: **4 x 4.0 = 16초** (SenseVoice 안정 범위 내)

### 3.5 버퍼 트리밍 전략 (향후 개선 방향)

현재는 단순 FIFO(맨 앞 청크 제거)이나, 보다 자연스러운 트리밍을 위한 전략들:

| 전략 | 방식 | 장점 | 단점 |
|------|------|------|------|
| **단순 FIFO** (현재) | 최대 N개 초과 시 맨 앞 제거 | 구현 단순, 예측 가능 | 문장 중간에서 잘릴 수 있음 |
| **규칙 기반** | ".","?","!" 문장 부호 기반 분리 | 추가 모델 불필요 | 한국어는 문장 부호 사용이 불규칙 |
| **Sentence Segmenter** | 문장 분리 모델 활용 | 자연스러운 문장 경계 | 추가 모델 필요, latency 증가 |
| **VAD 연동 초기화** | VAD 침묵 구간에서 버퍼 초기화 | 자연스러운 발화 단위 | VAD 의존성 |

추가 고려사항:
- **a-1:** VAD에 의해 나뉘어도 다음 문장 디코딩에서 이전 문맥 활용
- **a-2:** VAD 기반으로 나뉘면 청크 버퍼를 완전 초기화하여 새 문장 시작

### 3.6 Finalize: Tail 토큰 복구

right_trim으로 인해 마지막 청크의 끝 구간(~0.5초) 토큰이 커밋되지 않는다. finalize 단계에서 이를 복구한다.

**방식:** 재디코딩 없이, 마지막 `_feed_center_commit`의 디코딩 결과에서 `[chunk_dur - right_trim, chunk_dur]` 구간 토큰을 추가 추출

```python
# finalize 시:
tail_left = chunk_dur - right_trim   # 이전 center 끝 지점
# → [tail_left, chunk_dur] 구간 토큰 추출
# → dedup 후 committed_text에 추가
```

재디코딩 방식은 패딩에 의한 토큰 불일치로 중복/누락이 발생하여 폐기하고, 동일 디코딩 결과의 재추출 방식을 채택하였다.

## 4. 자막 병합: SubtitleStore

### 4.1 문제

1차(LIVE)와 2차(REFINE) 자막은 비동기로 도착한다. LIVE는 빠르지만 부정확하고, REFINE은 느리지만 정확하다. 사용자에게는 **하나의 일관된 자막**을 보여야 한다.

### 4.2 Overlay 알고리즘

```
confirmed_text (REFINE 누적):  "2026년 현재 음성인식 기술은"
live_text      (LIVE 최신):    "이천 십 오 년 현재 음성 인식 기술은 단순히 소리를"
```

1. 공백 제거 후 SequenceMatcher로 매칭
2. confirmed가 live의 어디까지 커버하는지 계산
3. live에서 confirmed가 커버하지 않는 **접미사(suffix)** 추출
4. `confirmed + suffix` = 최종 표시

```
결과: "2026년 현재 음성인식 기술은 단순히 소리를"
      ├─── REFINE (정확) ────┤├── LIVE suffix ──┤
```

REFINE이 진행될수록 confirmed 영역이 확장되어, 최종적으로 전체가 REFINE 품질로 교체된다.

## 5. 멀티프로세스 아키텍처

### 5.1 프로세스 구조

```
┌─── Main Process ───────────────────────────────────┐
│  AudioSource → 0.1초 프레임                          │
│                                                     │
│  transducer_task_q (maxsize=32) ──→ Transducer Proc │
│  transducer_event_q ←──────────────                 │
│                                                     │
│  refine_task_q (maxsize=1) ──────→ Refine Proc      │
│  refine_event_q ←───────────────                    │
│                                                     │
│  SubtitleStore ← 이벤트 병합                          │
│  Output ← Console / WebSocket                       │
└─────────────────────────────────────────────────────┘
```

- **spawn** 컨텍스트 사용 (fork 안전성 문제 회피)
- 각 워커가 **자체 프로세스에서 모델 로드** → GIL 회피, 진정한 병렬 처리
- Queue 기반 태스크/이벤트 통신

### 5.2 배압(Backpressure) 제어

refine_task_q의 maxsize=1로, 모델 처리 속도보다 빠르게 청크가 생성되면 메인 프로세스가 블록된다. 이때:

```python
def _put_task(task_queue, task):
    while True:
        try:
            task_queue.put(task, timeout=0.05)
            return
        except queue.Full:
            _drain_worker_events()  # 결과 큐 소비하며 대기
```

### 5.3 이벤트 드레인 공정성

REFINE은 처리가 느리고, LIVE는 빈번하다. 한쪽만 소비하면 다른 쪽이 밀린다:

```python
def _drain_worker_events():
    _drain_refine_events(max_items=8)      # REFINE 먼저 (느린 쪽 우선)
    _drain_transducer_events(max_items=16)  # LIVE
    _drain_refine_events(max_items=8)      # REFINE 한 번 더
```

## 6. 서버 아키텍처 (Web UI)

### 6.1 Persistent Worker Pool

서버 모드에서는 매 요청마다 모델을 로드하면 수 초의 지연이 발생한다. 이를 해결하기 위해 **서버 시작 시 워커를 미리 생성**하고, 모델을 메모리에 상주시킨다.

```python
class WorkerPool:
    def start(self):
        # 서버 시작 시 1회 실행
        # Transducer 워커 + Refine 워커 프로세스 생성
        # 모델 로드 후 대기 상태

    def new_run(self):
        # 각 요청마다 호출
        # 새로운 태스크/이벤트 큐 생성
        # 기존 워커에 "reset" 명령 → 상태 초기화
        # 모델 재로드 없음
```

### 6.2 WebSocket 프로토콜

```json
// 클라이언트 → 서버
{"action": "start", "path": "utt_0001.wav"}
{"action": "start_mic"}
{"action": "stop"}

// 서버 → 클라이언트
{"type": "subtitle", "tag": "LIVE|REFINE|LIVE-FINAL|REFINE-FINAL",
```

## 7. 평가 체계

### 7.1 평가 지표

| 지표 | 설명 | 계산 방식 |
|------|------|----------|
| **CER (Character Error Rate)** | 문자 단위 오류율 (공백 무시) | `1 - SequenceMatcher.ratio()` |
| **중복 감지** | 3자 이상 반복 부분 문자열 탐색 | `compact(text)`에서 부분 문자열 빈도 검사 |
| **RTF (Real-Time Factor)** | 처리시간 / 오디오시간 | `elapsed / audio_duration` |

### 7.2 평가 데이터

- 84개 한국어 발화 (data/utterances/*.wav)
- 각 2~20초, 16kHz mono
- 정답 레이블: data/label.txt

### 7.3 벤치마크 결과

| 전략 | CER (공백 무시) | RTF | 비고 |
|------|:---:|:---:|------|
| Full Text (기준선) | 4.54% | - | 전체 디코딩 |
| Simple Chunking (4.0초) | 8.77% | ~0.08 | 독립 청크 |
| Overlapped Center-Commit (4.0초/0.5초) | 5.48% | ~0.10 | 중첩 청크 |
| **Accumulated Context (4.0초/0.5초, max 4)** | **~5.5%** | **~0.10** | **현재 구현** |

### 7.4 평가 실행

```bash
python eval/eval_all.py 10
```
